# Odeion branding and compatibility

Pubky Music is now **Odeion**: the product and its apps are Odeion, the node's program is `odeiond`.
This page lists every surface that was renamed, every identity that kept its pre-Odeion name on
purpose, and why. `tools/branding-check.py` checks both lists in CI-able form; lines that keep the
old name on purpose say `compat: pre-Odeion`.

The rule: **names people see change; identities that installs, accounts and data depend on do not**.
Nothing is deleted, moved or migrated: a node, an app or an integration updates in place.

## Still "Pubky Music": the desktop app's installed name

The rename is **not finished for the desktop app's packages**. Its `productName` ("Pubky Music"),
`publisher` ("Pubky Music") and `mainBinaryName` (`pubky-music`) stay as they were, because Tauri
uses them as install identities (tauri-utils 2.10 config reference, `productName` and
`bundle.windows.wix.upgradeCode`). People still see the old name in these places:

| Platform | Where "Pubky Music" (or `pubky-music`) still shows |
| :-- | :-- |
| macOS | the `.app` name in Finder and Applications, the Dock and the menu bar (`CFBundleName`, `CFBundleDisplayName`), the `.dmg` volume |
| Windows | the installer's title and pages, the install folder, the Start menu entry, Settings › Apps (name and publisher), the process name `pubky-music.exe` |
| Linux | the launcher's name (`Name=` in the `.desktop` file), the `.deb` package name `pubky-music`, the program `pubky-music`, the AppImage's desktop entry |
| Android | nothing: the launcher label and activity title are Odeion (`android-patch.py` step 9; checked on a stand-in project, not an APK build) |

The window, its pages and dialogs say Odeion on every platform. The downloads keep their
`pubky-music-*` file names on purpose (published links).

What finishing it takes, without a second app being installed next to the first (not done here, not
built or tested here):

1. **Windows MSI:** pin `bundle.windows.wix.upgradeCode` to the code today's builds use (Tauri derives
   it from `<productName>.exe.app.x64`; `tauri inspect wix-upgrade-code` prints it), then rename, and
   test an MSI upgrade from the last release on Windows.
2. **Windows NSIS:** the install folder, Start menu entry and uninstall entry follow `productName`; a
   rename needs installer hooks (or a template) that find and remove the old install, tested from
   the last release on Windows.
3. **Debian:** a renamed package needs `bundle.linux.deb` `conflicts`/`replaces`/`provides:
   pubky-music`, tested as an upgrade with apt; or a desktop-entry template that changes only the
   launcher name.
4. **macOS:** an `Info.plist` merge can set the shown names (`CFBundleDisplayName`, `CFBundleName`)
   without touching the identifier; the `.app` folder name still follows `productName`. Needs a
   macOS build to check.
5. The updater (`latest.json`, the signing key) must carry each installed app to the renamed one:
   test from the last release on each platform.

Until then the branding change stays a draft for this part, and nothing claims the rename is done
everywhere.

## Settings in the environment: `ODEION_` and `PM_`

Every setting is now `ODEION_<NAME>`; `PM_<NAME>` still works for at least the next release.

- **One step at start**, `pm_model::brand::apply_env_compat()`, first thing in `odeiond`/`pm-node`,
  `pm-endpoint` and the desktop app (not on Android, which reads no settings), before any other
  thread and before any setting is read. It copies every `ODEION_<NAME>` onto `PM_<NAME>`, which the
  code reads. This is a prefix map rather than a list: every documented `PM_` setting has its
  `ODEION_` name, including the ones only the image's entrypoint reads.
- **The new name wins, even when empty:** `ODEION_X=""` with `PM_X=y` means X is empty (for most
  settings: "use the config file's value").
- **Values** pass through unchanged, Unicode or not.
- **Only our names:** a name after the prefix must be `A`–`Z`, `0`–`9`, `_`; other variables
  (`RUST_LOG`, `TAURI_*`, `ODEION_lower`, …) are left alone.
- **Log:** at start, at info level, one line names the settings read under their old names, and one
  names `ODEION_`/`PM_` pairs with different values. Names only, never a value. It is information,
  not an error: both spellings work this release. The same value under both names says nothing. On
  bare metal both shipped units set `RUST_LOG=info`, so the line is in the journal.
- **The image's entrypoint** does the same in `sh` before writing `node.toml`: `ODEION_NAME`,
  `ODEION_TOKEN`, `ODEION_FOLDERS`, … work with `docker run -e` and under a compose file's
  `environment:`. It then passes every `PM_` setting under its `ODEION_` name too, so in Docker the
  node reports no old names: the image's own defaults (`PM_LISTEN`, `PM_DATA_DIR`, `PM_FOLDERS`) and
  the shipped compose files still use `PM_` names, because an older image does not know `ODEION_`,
  and a user's `-e PM_LISTEN=…` must keep beating the image default.
- **The bundle's `.env`** (deploy/bundle): `ODEION_IMAGE`, `ODEION_TAG`, `ODEION_TOKEN`,
  `ODEION_NAME`, `ODEION_CONTACT` and `ODEION_PUBLIC_URL` are read before their `PM_` names
  (`setup.sh` still writes the `PM_` ones and adds none next to an `ODEION_` one). An empty
  `ODEION_NAME`, `ODEION_CONTACT` or `ODEION_PUBLIC_URL` wins; an empty token, image or tag counts
  as unset, because empty is never valid there. `backup.sh` and `restore.sh` read the token, the
  backup passphrase, the port and the node's config file the same way (`deploy/bundle/settings.sh`).
  `.env` values are read as compose's `.env` parser reads them (`dotenv_get`): quotes, spaces and
  an inline ` #` comment are dropped, so `ODEION_TOKEN=""` is empty and `"abc"` is `abc`. A value
  that starts with `#` stays a value (`ODEION_TOKEN= # x` is `# x` to compose too). Checked against
  the real `docker compose config` in `tools/bundle-settings-check.py`, which CI runs (`branding` job).
  `KEY: value` lines count too; a comment starts only at a space then `#` (a tab then `#` stays in the
  value). Not handled, and a follow-up: backslash escapes inside `"…"`, `$VAR`/`${VAR}` expansion and
  values over several lines. `setup.sh` writes hex values, so its own `.env` never needs them.
- **The token in the bundle:** `${ODEION_TOKEN:-${PM_TOKEN:-}}`, with no `:?` inside (Compose v2 checks
  an inner `:?` before the outer name). With no token at all the node makes its own and keeps it in
  its data folder, because it listens beyond localhost, so the API is never open
  (`crates/pm-node/src/api_token.rs`). `ADMIN_PASSWORD` still requires `setup.sh`. The node writes its
  `node.toml` once, so a token added to `.env` later is not the node's; the scripts therefore use the
  token the node uses (its config's `[api] token`, else the one it made), read without showing it
  or writing it to disk. The config's token line may be `"…"` (with `\"` and `\\`) or `'…'`, with a
  comment after it; anything else (`"""…"""`, other escapes, a bare value) stops the script with a
  message instead of falling back to another token. `backup.sh` asks the running node, then `.env`.
  `restore.sh` takes the backup's own token (its `node.toml`, else its `api-token`); without a
  `node.toml` in the backup, compose's (shell, then `.env`); when the restored node refuses it
  (401), the one the running node uses, read in its container; and it stops at once, saying where
  the token is, instead of waiting. `ODEION_TOKEN=…` in the shell counts only when the backup has
  none or its token line cannot be read. CI checks this on the runner's Compose v2; it was
  also checked locally on v5.5.1 and v2.40.3.
- **Backups from before Odeion:** `restore.sh` tries the passphrase as compose reads `.env`, then as
  written there (how `backup.sh` read it up to v0.2.2: quotes and comment included), then the one
  `backup.sh` made when it found none (`node/passphrase`). It moves on only when the node answers
  "That passphrase does not open this backup", and restores without the sign-ins only when there is
  no passphrase at all.
  Other `.env` keys (`ADMIN_PASSWORD`, `MUSIC_DIR`, …) never had a `PM_` name and are unchanged.
- **TrueNAS:** its settings are written under `environment:` in the YAML; an `ODEION_` key there
  works as in `docker run -e`.
- **The Roon bridge** (`sidecars/roon-bridge`) reads `ODEION_NODE` and `ODEION_TOKEN` first, then
  `PM_NODE` and `PM_TOKEN`; the `ODEION_` one wins, also when empty.
- **Build-time values** (`ODEION_PROJECT_*`, `ODEION_NODE_VERSION`, `ODEION_UPDATE_CHANNEL`): the
  `ODEION_` value when set (even empty), else the `PM_` one (`pm_model::brand::build_env`). The
  release workflow keeps passing the repository variables under their `PM_` names; no value is
  printed (`build.rs` prints only `rerun-if-env-changed` names).

## Moving to `odeiond.service`

`deploy/bare-metal/odeiond.service` is the unit for new installs. `pubky-music-node.service` stays,
unchanged in what it runs (`pm-node`, the same program), for existing installs and the published
install commands. Both use the same user, config file and data folder, and both log at info level
(`RUST_LOG=info`). Each has `Conflicts=` with the other, and `odeiond.service` has
`After=pubky-music-node.service` (one ordering edge, none back, so no cycle): starting either while
the other runs stops the other first, so the port is free. There is deliberately no
`Alias=pubky-music-node.service`: an alias cannot be enabled while the old unit file is installed,
and it would not replace it.

To move (also in `docs/guides/install-linux.md`), keep what was changed locally: an extra folder in
`ReadWritePaths=` (the backup guide adds one), `Environment=` lines, and drop-ins.

```sh
systemctl cat pubky-music-node      # the old unit as it runs: its file, then its drop-ins
sudo install -m 755 odeiond /usr/local/bin/ && sudo ln -sf odeiond /usr/local/bin/pm-node
sudo install -m 644 odeiond.service /etc/systemd/system/
sudo mkdir -p /etc/systemd/system/odeiond.service.d
[ ! -d /etc/systemd/system/pubky-music-node.service.d ] ||
  sudo cp -a /etc/systemd/system/pubky-music-node.service.d/. /etc/systemd/system/odeiond.service.d/
sudo systemctl edit odeiond         # lines edited in the old unit's own file, e.g. ReadWritePaths=/mnt/backup
sudo systemctl daemon-reload
systemctl cat odeiond               # the same ReadWritePaths= and Environment= as before
sudo systemctl disable --now pubky-music-node && sudo systemctl enable --now odeiond
```

Going back is the same with the names swapped. Nothing is deleted.

## Checks

- `python3 -I tools/branding-check.py`: Odeion where people look, the identities above unchanged,
  and "Pubky Music" only in history and marked compatibility lines.
- `cargo test -p pm-model --test brand_env`: the environment plan (new, old, both, empty, Unicode,
  non-Unicode, other variables, no values in the log).
- `cargo test -p pm-node --test odeiond`: `odeiond` and `pm-node` with a cleared environment; a
  loopback-only node reads the new name, the old name, and prefers the new one even empty.
- `cargo test -p pm-endpoint --test odeion`, the desktop app's `update` tests, the web app test
  `the_web_app_is_called_odeion` (PWA manifest).
- `python3 -I tools/entrypoint-check.py`: the image's entrypoint with a stand-in `odeiond`.
- `python3 -I tools/release/android-label-check.py`: the Android patch on a fictional generated
  project (label Odeion, application id unchanged). It does not build an APK; the release
  workflow's Android job does.
- Home Assistant: `integrations/home-assistant/tests` (`Names`).

## Rollout checklist (beyond the names)

The rename ships with nothing else. What listeners asked for is tracked in its own work and is
**not** part of this change or claimed by it:

- [ ] Every sign-in and provider method explains itself inline, step by step, numbered.
- [ ] Albums are separate from EPs and singles.
- [ ] On phones and tablets, Sources, navigation and actions are reachable.
- [ ] Slow loading, errors, copies running in the background and restarts each say what is
      happening.
- [ ] Each listener uses their own streaming accounts; nobody plays with someone else's.
- [ ] Diagnostics stay off by default, switched on separately and visibly; no hidden tracking.
- [ ] After merge: the owner decides on the repository and image names, the desktop
      `productName` migration (above), and when `pm-node` and the `PM_` names stop being read.
- [ ] The Linux installer ISO is separate work, after this rename.
